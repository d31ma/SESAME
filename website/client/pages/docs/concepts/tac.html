Concepts

Nine words that mean something specific in SESAME. If you read only one page before writing code, read this one — most confusion later is a word that meant something slightly different in the last system you used.

Tenant

The strongest isolation boundary in a shared deployment. Every tenant-bound record carries its tenant, and the check happens below the query you construct, so a caller cannot reach across a boundary by asking cleverly.

If you are building a single-organisation product, you still have one tenant. Bootstrap it once; it is idempotent per normalised name, so a retry after a timeout returns the existing tenant rather than making a second one.

Principal

A human or a workload — the thing that authenticates and that decisions are made about. Not a "user": a service account is a principal too, and having one word for both is what keeps the authorization model from growing a parallel path for machines.

A principal is active or suspended. Suspension is durable and immediate: it survives a restart and denies with deny_principal_suspended rather than falling through to a grant check.

Identifier

A namespaced handle a principal can be found by — email:alice@example.com, login:alice, employee_id:1234. The namespace is yours to choose.

Identifiers are normalised and claimed atomically and uniquely within a tenant. Two concurrent creations for the same normalised value cannot both win; one gets identifier_conflict.

Authenticator

A credential or factor belonging to a principal: a password, a TOTP secret, a set of recovery codes, a passkey. A principal may hold several, and which ones were used determines the session's assurance.

Authentication transaction

The short-lived, persisted state machine a login runs in. It exists because a login is rarely one call — a password, then a second factor, then completion — and because that sequence has to survive a restart and bound its own attempts.

You will see it in every login snippet as transaction_id. It is not a session; it becomes one only at authn.complete.

Session

A bounded, revocable authenticated context. It is two values: an session_id, which is a handle, and a session_secret, which is the proof. The secret is returned exactly once and stored only as a SHA-256 digest, so a stolen data root does not yield usable sessions.

Revocation is durable and immediate, and it cascades: revoking a session revokes every refresh-token family issued on it.

Assurance

How strongly the session's holder was authenticated. Three levels:

  • password — one factor SESAME verified itself.
  • mfa — two factors, or one passkey with user verification.
  • federated — an external provider vouched for them and SESAME did not witness the credential.

federated is deliberately not password. Collapsing them would let a federated login walk past a policy that requires a second factor, however the provider actually authenticated the person.

Role, permission, grant

A permission is an action–resource pair, optionally with equality conditions on context. A role is an immutable, named set of permissions. A grant attaches a role to a principal or to a group.

Roles are immutable on purpose: changing what a role means in place would silently rewrite the meaning of every grant that points at it. Create a new role and move grants instead.

Decision and policy version

A decision answers one question — may this principal perform this action on this resource — with allow/deny, a stable reason_code, and the policy_version it was decided under.

The policy version is the sequence number of the last policy-changing event. Pin it and you get repeatable decisions across a batch; read it back and you can prove which rules produced an answer in an audit. See Authorization.
