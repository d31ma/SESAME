Authentication and tokens

How a password becomes a session, and how a session becomes a JWT — with a working call sequence for each step in all ten languages.

1. Password to session

Authentication is a persisted transaction, not a single call. It survives a restart, it bounds its own attempts, and it is what a second factor attaches to.

authn.begin succeeds whether or not the identifier resolves. That is deliberate: an endpoint that failed differently for unknown accounts would be an enumeration oracle, so the difference only appears when a factor is verified.

The session secret is returned exactly once. SESAME stores a SHA-256 digest, never the secret, so a stolen FYLO root does not yield usable sessions.

2. Using and ending a session

Revocation is durable and immediate. It survives a restart, and it also revokes every refresh-token family issued on that session — otherwise signing out would leave long-lived tokens alive behind it.

3. Session to JWT

SESAME opens no port, so your application owns the /authorize, /token, and callback routes. The engine makes every protocol decision behind them; your routes move bytes and run your own login page.

Tokens come from the authorization-code flow rather than directly from a password, and that is what binds them to one client, one redirect URI, and one request. An OIDC client here has no grant_types field at all, so the password and implicit grants cannot be switched on by configuration or by mistake.

Three properties are worth knowing. The authorization request is validated before anyone is shown a login form, so a broken or hostile request fails early rather than after someone has typed a password. The interaction secret authorizes completing exactly one interaction, which is what stops a confused-deputy attack across clients. And the code is single-use and short-lived: redeeming it twice is refused.

Every token-exchange failure returns one undifferentiated invalid_grant. A caller that could tell a spent code from a wrong verifier from a mismatched redirect URI would learn the shape of the flow.

4. Refreshing

Request the offline_access scope and the token response carries a refresh token. Refresh tokens rotate: each response replaces the token you presented, and presenting a spent one revokes the entire family — that is how a stolen token is detected rather than merely expired. 

tokens = client.token_exchange({
    "grant_type": "refresh_token",
    "refresh_token": previous_refresh_token,
    "client_id": client_id,
    "client_secret": client_secret,
})

# The new refresh_token replaces the old one. Store it before you use it;
# a crash between the two leaves you holding a token that is already spent.

A refresh checks that the underlying session is unrevoked, not merely unexpired. Otherwise offline_access would outlive signing out, which would make revocation meaningless.
